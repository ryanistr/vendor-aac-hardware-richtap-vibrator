# lmvibrator — source-built OPLUS linear-motor HIDL HAL

Source for `vendor.oplus.hardware.lmvibrator@1.0::ILinearMotorVibrator`, the
interface `VibratorManagerService` uses for every OPLUS effect haptic (touch,
keyboard, notification, alarm, fingerprint feedback) when
`oplus.software.vibrator_lmvibrator` is enabled.

It replaces the shipped prebuilt `/odm/bin/hw/vendor.oplus.hardware.lmvibrator@1.0-service`,
which drives `/sys/class/leds/vibrator/*` — a node set the X6739 (AW862xx,
`aw862xx_haptic.ko`) does not have, so the stock binary could never move this
motor.

## Layout

```
1.0/ILinearMotorVibrator.hal      interface, recovered from the framework's
                                  Java proxy + the vendor .so symbol table
service/                          the service: pattern playback, durations
build/build_hidl_gen.sh           builds AOSP hidl-gen on the host (no Soong)
build/build_lm_hal.sh             cross-builds the service with the NDK
tools/build_patterns.py           OOS15 RTP firmware -> patterns/patterns.tsv
tools/dur.sh, tools/haptic_tune.sh  on-device duration benches (root)
patterns/patterns.tsv             readable per-waveform segment table
NOTES.md                          evidence, reverse-engineering notes, tuning
```

## Build

```sh
# 1. host hidl-gen: needs these AOSP checkouts under build/aosp/
#    system/tools/hidl, system/libbase, system/libhidl, system/libhwbinder,
#    system/core (libutils, libcutils, libsystem), system/logging,
#    system/libfmq, external/libcxx, external/jsoncpp, external/fmtlib
./build/build_hidl_gen.sh

# 2. the service (aarch64, links the device's libhidlbase/libhwbinder)
NDK=/path/to/android-ndk ./build/build_lm_hal.sh
```

`build/` is git-ignored: the generated HIDL sources and the AOSP checkouts are
reproducible from the scripts, they are not part of this tree.

## Install on the X6739 port

| artefact | path | why that path |
|---|---|---|
| service binary | `/vendor/bin/hw/android.hardware.vibrator@1.0-service-mediatek` | an existing `hal_vibrator_default_exec` label, so it runs in `hal_vibrator_default` without a new SELinux rule |
| init | `/vendor/etc/init/vendor.oplus.hardware.lmvibrator@1.0-service.rc` | starts the service in `class hal` |
| VINTF | `/vendor/etc/vintf/manifest/manifest_oplus_lmvibrator.xml` | `registerAsService()` refuses to register a HIDL interface that is not in the manifest |
| patterns | `/vendor/etc/vibrator/patterns.bin` | generated by `tools/build_patterns.py` from `patterns/patterns.tsv` |

## How it plays a haptic

The HIDL call carries only a waveform id, an amplitude and an RTP flag, so the
service:

1. looks the waveform up in `patterns.bin` (segments of start/duration/peak
   extracted from the OPLUS RTP firmware), falling back to a single pulse;
2. plays each segment through the driver's `duration` + `activate` path, which
   is the only one that runs `ram_config` and therefore the only one that can
   change the felt weight;
3. applies a fixed correction table for effects whose name contradicts the
   extracted data (fingerprint enroll success/failure, clear-all,
   notification light/short, game weak, long-press and two/three-finger long).

Amplitude (`gain`) is inert on this chip, so intensity is expressed purely as
pulse length. The measured buckets, the dead-end amplitude levers and every
tuning decision are documented in [NOTES.md](NOTES.md).
