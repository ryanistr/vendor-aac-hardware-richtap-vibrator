# OPLUS linear-motor vibrator HIDL — reconstruction notes

## What this is

Reverse-engineered source for:

    vendor.oplus.hardware.lmvibrator@1.0::ILinearMotorVibrator/default

built as `/vendor/bin/hw/vendor.oplus.hardware.lmvibrator@1.0-service`.

The original binary was shipped prebuilt in the OOS15 donor:

    oos15_old/erofs/odm/bin/hw/vendor.oplus.hardware.lmvibrator@1.0-service
      ELF 64-bit LSB pie, ARM aarch64, stripped, 38296 B
      BuildID md5/uuid = 7a9fd4da1ebb4b3e2bebc019530638db

## How the interface was recovered

1. **Method set** — demangled symbols in the generated interface library
   `lib64/vendor.oplus.hardware.lmvibrator@1.0.so`, filtered to the
   `BpHwLinearMotorVibrator::` / `BnHwLinearMotorVibrator::_hidl_` names:

       linearmotorVibratorOn(int, short, bool)
       linearmotorVibratorOff()
       setVmax(int)
       getStatus() -> int
       getVibratorTouchStyle() -> int
       setVibratorTouchStyle(int)
       write_gun_type(int)
       write_gun_mode(int)
       write_bullet_num(int)
       write_haptic_audio(hidl_string const&)

2. **Declaration order / transaction ids** — `BnHwLinearMotorVibrator::onTransact`
   dispatches a `switch` whose cases are emitted in transaction order, starting
   at `FIRST_CALL_TRANSACTION` (1). Disassembly of the dispatcher gives:

       tx 1  _hidl_linearmotorVibratorOn      tx 6  _hidl_getStatus
       tx 2  _hidl_setVmax                    tx 7  _hidl_write_haptic_audio
       tx 3  _hidl_getVibratorTouchStyle      tx 8  _hidl_write_bullet_num
       tx 4  _hidl_write_gun_type             tx 9  _hidl_write_gun_mode
       tx 5  _hidl_linearmotorVibratorOff     tx 10 _hidl_setVibratorTouchStyle

   The range check `cmp w8, #0x9` confirms exactly 10 methods.

3. **Behaviour** — string literals in the service's `.rodata`:

       /sys/class/leds/vibrator/vmax
       /sys/class/leds/vibrator/gun_mode
       /sys/class/leds/vibrator/gun_type
       /sys/class/leds/vibrator/haptic_audio
       /sys/class/leds/vibrator/bullet_nr
       /sys/class/leds/vibrator/brightness
       /sys/class/leds/vibrator/waveform_index
       /sys/class/leds/vibrator/rtp
       /sys/class/leds/vibrator/rtp_going
       /proc/vibrator/touch_style
       "<awinic debug> open dev  fail"
       "node write error,ret = %d"
       "node write success,ret = %d"
       "111  laibaoquan get hidl"
       "222  laibaoquan set touchstyle hidl"
       "VibratorService"

   Imported symbols confirm the I/O model: `__open_2`, `write`, `close` for the
   sysfs writes; `fopen`, `fread`, `fseek*`, `fclose` for the `/proc` readback.

## Uncertain / inferred

- **Return types.** HIDL return types are not mangled, so `generates (int ...)`
  is inferred from the "ret = %d" logging, not proven.
- **`getStatus()` semantics.** No dedicated status node appears in `.rodata`;
  the reconstruction re-reads touch_style.
- **`linearmotorVibratorOn` third parameter.** Recovered as `bool` from the
  proxy symbol; its meaning ("gun mode") is a guess from the sibling
  `gun_*` nodes.
- **Interface hash.** Not extracted; a byte-exact ABI clone requires the
  original `.hal`, which would also give exact hash + return types.

## Status: superseded by the Rust AIDL port

This HIDL C++ reconstruction is kept as reverse-engineering documentation.
The shipping implementation is now the Rust + AIDL port inside
`vendor-aac-hardware-richtap-vibrator` (`src/lmvibrator.rs` +
`aidl/vendor/oplus/hardware/lmvibrator/ILinearMotorVibrator.aidl`), which
builds with the NDK/cargo toolchain and additionally falls back to
`/sys/class/leds/vibrator_single` so it works on the X6739. The prebuilt HIDL
binary is no longer shipped in the ROM.

## Build status: BLOCKED — no HIDL toolchain on this host

Verified absent:

    hidl-gen                         not found anywhere on disk
    system/libhidl headers           not present (no HidlSupport.h, no IBase.h)
    gn / ninja / Soong               not installed
    NDK HIDL support                 none (NDK ships no HIDL headers/libs)
    rsbinder (0.6 / 0.10 / 0.12)     AIDL only; no hwbinder/HIDL support

Compile attempt against the NDK:

    $ aarch64-linux-android34-clang++ -std=c++17 -fsyntax-only service.cpp
    service.cpp:27:10: fatal error: 'android/hardware/hidl.h' file not found

HIDL C++ cannot be produced with the NDK alone: the interface header must be
generated by `hidl-gen`, and the service must link `libhidlbase` /
`libhwbinder` (both exist in the ROM tree, but without headers they cannot be
used from source).

### To unblock

Provide an AOSP HIDL toolchain, then:

    hidl-gen -o out -Lc++-sources -rvendor.oplus.hardware:vendor/oplus/hardware \
             1.0/ILinearMotorVibrator.hal
    hidl-gen -o out -Lc++-headers -rvendor.oplus.hardware:vendor/oplus/hardware \
             1.0/ILinearMotorVibrator.hal

and build `service.cpp` against the generated headers plus libhidlbase,
libhwbinder, libutils, libbase, liblog and the existing
`vendor.oplus.hardware.lmvibrator@1.0.so`.

## Does this HAL matter on the X6739?

Yes — this is the HAL the framework actually uses for OPLUS effect haptics on
this port. `VibratorManagerService` composes touch, keyboard, notification and
alarm effects into `OplusVibrationEffectSegment`s, converts them to
`OplusPrebakedSegment`s, and `PerformOplusPrebakedStep.play()` calls
`OplusVibratorHalWrapper.linearMotorVibratorOn()` → the HIDL
`ILinearMotorVibrator` served here. Verified on device (launcher long-press):

    VibratorManagerServiceExtImpl: effect=Composed{segments=[OplusVibrationEffectSegment{mEffectId=69}]}
    VibrationThread: Perform OplusPrebakedSegment{mWaveformId=6, mDuration=45, mEffectStrength=2400}
    LmVibratorHAL: on: waveform=6 amplitude=2400 gain=255

The wrapper only falls back to `OplusVibratorManager` (the AIDL
`vendor.oplus.hardware.oplusvibrator.IOplusVibrator`) when the
`oplus.hardware.vibrator_oplus_v1` feature is present; it is not, so the HIDL
path is the live one. `oplus.software.vibrator_qcom_lmvibrator` must also stay
absent: with it set, `PerformOplusPrebakedStep` bypasses this HAL and calls
`performExtPrebaked` instead.

## Trigger nodes: why exactly one write may start the motor

The original targets the AW8697 node set (`waveform_index`, `vmax`, `rtp`,
`rtp_going`, `gun_type`, `gun_mode`, `bullet_nr`, `haptic_audio`,
`/proc/vibrator/touch_style`). The X6739 has an **AW862xx** instead, driven by
`/vendor/lib/modules/aw862xx_haptic.ko` (klog tag `haptic_nv`):

* `brightness` is the LED-class trigger, and its value is the **duration in ms**
  (`aw8624->state = value; aw8624->duration = value;` then an hrtimer). The LED
  class clamps it to `max_brightness` = 255, so this path can never express an
  effect longer than 255 ms.
* `duration` + `activate=1` runs `vibrator_work`, which picks the RAM wave by
  duration (`ram_config: duration %d, select index %d`) and arms the driver's
  own timer: this is the only path that honours real effect lengths (1 ms .. 60 s).
* `index` selects a RAM wave, but the firmware holds very few waves and the
  driver rejects anything above `ram_num`
  (`index_store: input value out of range!` for id 6, and only ~1.7 KB of RAM
  firmware). OPLUS waveform ids (41..443) are therefore not addressable — a
  per-ringtone pattern cannot be reproduced on this chip.
* `gain` is the amplitude and is applied at playback time
  (`ram_vbat_comp: ram vbat comp close, set_gain 0xNN`), so the OPLUS stepless
  intensity (0..2400, scaled to 0..255) reaches the motor on this path.
* `rtp` takes a *firmware file index* (0..3), not a waveform id, and starts an
  RTP playback by itself — writing it alongside `brightness` is what made every
  effect play twice.

Default trigger replays the **real** waveform for the requested id, extracted
from the OOS15 tree this port came from:

    oos15_old/erofs/odm/firmware/*_RTP_<waveform_id>[_<freq>Hz].bin

Those are the OPLUS per-effect RTP waveforms (8-bit unsigned amplitude at
24 kHz; verified by duration — id 41 is 65,633 B = 2729 ms = symphonic).
File names come in two shapes and both are indexed: `..._RTP_<id>_<freq>Hz.bin`
and `..._<name>_<id>_<freq>HZ.bin` (the second form is where the ringtone
waveforms live, e.g. `aw8697_Newfeeling_98_165HZ.bin`).
`tools/build_patterns.py` matches each id against `effect_waveform.xml`, picks
the variant whose length fits, converts it to segments
`(start_ms, duration_ms, peak_amplitude)` and writes
`/vendor/etc/vibrator/patterns.bin` (~52 KB, 217 waveforms: 102/114
RINGTONE, 67/94 NOTIFICATION, 30/47 ALARM, 18/106 TOUCH). The HAL loads that
table at startup and replays the segments as LED-triggered pulses scaled by the
user intensity; ids without a file keep the single-pulse fallback.

Two corrections learned on device: the pattern is shifted so its first pulse
starts at t=0 (many files begin with up to 3 s of leading silence that exists
only to align with the sound — the HAL is called at t=0, so a short effect
otherwise played nothing), and only files whose length matches the XML
duration within 15 % are accepted, so nothing plays at the wrong speed.

Example (heartbeat, id 43): pulses at 0 / 360 / 1320 / 1680 / 2640 ms — the
original rhythm, not a synthesised train.

Modes (runtime, no rebuild):

    setprop persist.sys.lm.mode pattern     # default: real extracted waveform
    setprop persist.sys.lm.mode plain       # single pulse, no pattern
    setprop persist.sys.lm.mode activate    # driver-chosen wave (heavy/looped)
    setprop persist.sys.lm.mode index       # RAM wave only (ids are limited)

Each segment also carries a **character** derived from its own envelope
(tick <=30 ms, click <=80 ms, thud <=250 ms, heavy above that) and the HAL
plays the matching RAM wave instead of reusing one:

    tick 5404 (60%) · click 697 (8%) · thud 1871 (21%) · heavy 1049 (12%)

**Intensity is pulse duration, and `duration` + `activate` is the only path
that honours it.** Confirmed by tracing TWRP live in recovery (its working
slider), which writes:

    slider 39  -> duration_store: duration=39,  activate_store: value=1
    slider 120 -> duration_store: duration=120, activate_store: value=1
    slider 300 -> duration_store: duration=300, activate_store: value=1
    gain stays 0x80 the whole time

and the driver then selects the RAM wave from that length:

    ram_config: duration 39,  select index 1
    ram_config: duration 120, select index 4
    ram_config: duration 300, select index 4

The LED `brightness` trigger never calls `ram_config`, which is why gain,
duty-cycle and brightness tricks all felt identical. The HAL therefore plays
through `duration` + `activate=1` and stops with `activate=0`.

Durations written (tuned on device, half of TWRP's range):

    short effects (<=80 ms: touch, keyboard, clicks)  15..50 ms
        -> stays a click even at full intensity; riding the full ladder here
           turned every key press into a thud
    long single pulses                   20 / 60 / 90 / 200 ms by slider tier
        -> measured by ear: click / tick / thud / heavy

The actuator quantises duration into felt buckets (measured with tools/dur.sh):

     1.. 50 ms  -> click            HAL writes 20
    60.. 80 ms  -> tick             HAL writes 60
    90..180 ms  -> thud             HAL writes 90
   190..300 ms  -> heavy            HAL writes 200
  >300 ms       -> driver loops its "long vibration" wave, avoid

Each ladder value is the shortest duration inside its bucket, so it produces the
intended character with the least motor time and battery cost.

Some effects had to be corrected by hand because their extracted data (or the
intensity ladder) contradicted what they are for. These play fixed durations and
ignore the ladder:

    wave 3     -> 20 ms        fingerprint enroll success (was 110 ms heavy)
    wave 6     -> 200 ms       fingerprint enroll failure (was 45 ms click)
    wave 254   -> 60 ms        effect_notification_light (was 200 ms heavy)
    wave 342   -> 60 ms        effect_notification_short_2
    wave 47    -> 40 ms        "clear all notifications" (effect_customized_spread_out)
    wave 363   -> 40 ms        recents "clear all" (one_key_clear_recent_task_feedback)
    wave 414   -> 50 ms        game_custom_vibration_weak
    wave 65537 -> 90 ms        input_method_long_press_effect
    wave 171   -> 90 ms        effect_other_threefingers_long
    wave 178   -> 90 ms        effect_other_twofingers_long
    wave 46    -> 110+110 ms   effect_moderate_short_vibrate_twice (two hits)

Wave 112 (`effect_other_keyboard_strong`) is deliberately left at the tap clamp
so keyboard taps stay clicks.

Dense waveforms are de-chattered: runs of <=60 ms segments spaced <=30 ms apart
(the charging animation encodes one click as nine such pieces) are merged into a
single click, and no segment may run past the gap before the next one.
    pattern segments                     0.4x / 0.75x / 1.0x / 1.6x, max 200 ms

Verified from logcat on a keyboard: `on: waveform=105 ... dur=66 -> 50 ms`,
i.e. a key tap is a 50 ms click, not a thump.

The wave slot can also be forced, and each one was classified by ear:

    slot 0 = clicks (light)   slot 1 = thud (medium)   slot 3 = heavy
    (slots 2/4 buzz, 5 hums; unused)

`ram_num` reports 5, so slots 0..5 exist, but 6/7 are rejected by the driver.
A segment's kind shifts it up/down the ladder, so patterns keep their texture
while the slider moves the whole thing.

The slot mapping is tunable on device:

    setprop persist.sys.lm.waves "1,1,5,4"   # tick,click,thud,heavy
    setprop persist.sys.lm.wave 3            # force one slot, to audition it

All paths are logged on every call as `mode=…`, and every write failure is
logged with the resolved path.
